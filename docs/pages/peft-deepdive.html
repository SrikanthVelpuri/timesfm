PEFT methods — LoRA, DoRA, QLoRA, IA3, and friends

The foundation-model decision is binary (TimesFM yes/no). The fine-tuning decision is a tree: full FT → PEFT → which PEFT method → rank / target modules / merge strategy. This page is the math + tradeoff deep-dive of every PEFT method that matters in 2026: LoRA, DoRA, QLoRA, IA3, Adapter, Prefix Tuning, P-Tuning v2, LongLoRA, VeRA. finetuning.html says which we shipped (LoRA rank-8); this page says why, and what would change with a different problem.

TL;DR. LoRA decomposes a weight delta into two low-rank matrices — trainable params Θ(rank × d_model) instead of d_model2. DoRA further decomposes pretrained weight into magnitude + direction; matches full FT accuracy where LoRA leaves a gap. QLoRA quantizes the base to NF4 so a 70 B model trains on a single 48 GB GPU. IA3 is the cheapest (< 0.01% trainable params) but matches LoRA only on simple tasks. Prefix Tuning attaches learnable virtual tokens; loses accuracy at scale. We ship LoRA rank-8 on attention; we benchmarked DoRA (+0.2 pp MAPE, +12% latency at training time, no inference overhead) and have it on the watch list.

Why PEFT, in one paragraph

Full fine-tune of TimesFM 2.5 (200 M parameters): 200 M trainable, one optimizer state per param, one full activation cache. ~24 GB GPU memory peak, $640/quarter compute, one fully-fine-tuned model per route family = 20+ separately-audited artefacts. Catastrophic forgetting on cold-start (we measured: 10.2% → 14.7% MAPE). PEFT trains 0.1–1% of the parameters, fits in < 8 GB memory, $7/quarter, one base model + small adapters, and preserves cold-start because the trunk doesn't move. Same accuracy on the routes you care about. This is not a close decision; if your foundation model has > 100 M parameters, PEFT is correct.

The eight methods that matter

1 · LoRA — Low-Rank Adaptation (Hu et al. 2021)

The default. For each weight matrix W of shape (d_in, d_out) you want to fine-tune, freeze W and add a learnable delta ΔW = BA, where B is (d_in, r) and A is (r, d_out). The rank r is small (typically 4–64), so trainable parameters are r×(d_in + d_out) instead of d_in×d_out. Output is h = (W + α/r × BA) x. 

Forward pass:                       Memory profile:
  W is frozen, fp16/bf16             - W: read-only base, fp16
  delta = (alpha/r) * (B @ A)        - B, A: trainable, fp32
  h = (W + delta) @ x                - optimizer state on B,A only
                                     - activations: only what's needed
For TimesFM 2.5 attention:           for the rank-r delta
  W shape:        (1280, 1280)
  rank r:         8
  trainable:      2 * 8 * 1280 = 20,480 params per matrix
  vs full:        1,638,400 params per matrix (80x reduction)

Three implementation knobs that matter in production:

  • Target modules. Q, K, V, O of attention; or also up/down/gate of MLPs. Empirically, attention-only is 80% of the win at 30% of the cost; we ship attention-only.
  • Rank r. 4 / 8 / 16 / 32. Diminishing returns past 16 on TS panels. We ship rank 8 after a sweep.
  • Alpha α. Scaling factor; conventionally α = 2r. Loosely a learning-rate substitute for the LoRA delta.

LoRA can be merged: at inference, compute W′ = W + α/r BA once and use W′ everywhere. Zero inference overhead. This is what we do: 13 family adapters → 13 merged variants in pinned memory, hot-swap by pointer. See finetuning.html for the production serving story.

2 · DoRA — Weight-Decomposed Low-Rank Adaptation (Liu et al. 2024)

Decompose every pretrained weight W into magnitude m (one scalar per output column) and direction V (the column-normalized matrix), so W = m · V/||V||. Fine-tune both: m gets trained directly, V gets trained via a LoRA-style low-rank delta. The intuition: LoRA conflates magnitude and direction updates; DoRA separates them, matching full-FT accuracy where LoRA leaves a gap. 

Decomposition:            Forward pass:
  W = m * V / ||V||         V' = V + B @ A            (low-rank delta on direction)
  m: (1, d_out), trainable  W' = m * V' / ||V'||      (re-normalize)
  V: (d_in, d_out), frozen
  B, A: trainable

DoRA is a drop-in replacement for LoRA: same target modules, same merge story (the magnitude vector merges into the weight at inference). Empirically it closes the LoRA-vs-full-FT gap on most tasks. Cost: ~12% slower training step (extra normalization), no inference overhead after merge.

For us: we benchmarked DoRA on the 141-route panel. It gained 0.2 pp MAPE on the most fine-tunable family (no help on cold-start, as expected). Worth it eventually; not worth a re-deploy this quarter. It's on the next-refresh watch list.

3 · QLoRA — Quantized LoRA (Dettmers et al. 2023)

Three additions to LoRA, all about training memory. (1) Quantize the base model to NF4 (4-bit NormalFloat, an information-theoretically optimal data type for normally distributed weights). (2) Double quantization: quantize the quantization constants too, saving ~0.37 bits per parameter. (3) Paged optimizers: optimizer state is paged to CPU RAM, smoothing memory spikes during forward and backward passes. Net result: a 65 B parameter model fine-tunes on a single 48 GB GPU. 

Storage data type:          NF4 (4-bit, 16-bin scheme spaced by Gaussian quantiles)
Computation data type:      BF16 (16-bit BrainFloat) for forward/backward
Trainable params:           LoRA on top of NF4-quantized base
Memory:                     base @ 4-bit + LoRA @ fp32 + paged optimizer
For TimesFM 2.5 (200M):
  full base in fp16:           400 MB
  full base in NF4:            100 MB
  saves 300 MB; not worth complexity for a 200M model

QLoRA is the right answer for >= 7 B parameter base models where 16-bit weights don't fit on consumer GPUs. For TimesFM 2.5 at 200 M it's overkill — 400 MB fp16 base fits easily on any GPU. We don't use it; we'd revisit if a 1 B sparse-MoE TS model lands.

4 · IA3 — Infused Adapter (Liu et al. 2022)

Most parameter-efficient method that's competitive: rescale keys, values, and the inner activations of the FFN by a learned vector (element-wise multiplication). For T0-3B, IA3 had 0.01% trainable parameters — ~10× fewer than LoRA — while matching or beating LoRA on few-shot tasks. 

Self-attention: K' = K * lk        # lk is (d_head,) learned
                V' = V * lv        # lv is (d_head,) learned
FFN:           h' = h * lff       # lff is (d_ff,) learned
For TimesFM 2.5 attention:
  trainable per layer:  3 * d_head = 240 params (vs 20,480 for LoRA r=8)

IA3 wins on tasks that are essentially “turn the knobs” on the existing weights — few-shot classification, simple prompt-following. It loses to LoRA when the task requires learning new directions (genuinely new feature interactions). For TS forecasting we benchmarked: IA3 at 4.2 pp worse MAPE than LoRA rank-8, because the family-specific signal isn't a rescaling of the pretrained weights.

5 · Adapter — Houlsby / Pfeiffer (2019)

The original PEFT method. Insert a small bottleneck MLP after each transformer sublayer: down-project from d_model to d_bottleneck (typically 64), non-linearity, up-project back to d_model, residual. Train the bottleneck only. 

x  -> transformer sublayer -> h
h  -> LayerNorm -> W_down -> ReLU -> W_up -> (h + residual)
For TimesFM 2.5:
  d_model = 1280, d_bottleneck = 64
  trainable per layer: 2 * 1280 * 64 = 163,840 params

Adapter inserts new layers — meaning inference is slightly slower (extra matmul per sublayer) and the parameter count grows with depth. LoRA superseded Adapter because LoRA can merge into existing weights and has no inference overhead. Adapter is still useful when you want to swap multiple adapters at inference without re-merging.

6 · Prefix Tuning (Li & Liang 2021)

Don't modify any weights. Instead, prepend k learnable “virtual tokens” to the input of every attention layer's key and value (so attention attends to virtual tokens + real tokens). Train only the virtual tokens, ~0.1% of parameters. 

For each attention layer:
  K' = [P_k; K]                # P_k is (k, d_head) learnable prefix
  V' = [P_v; V]
  attention attends over k + L tokens
For TimesFM 2.5, k = 30:
  trainable: 30 * 2 * d_head * num_layers = ~150K params

Prefix Tuning was a clean idea but underperforms LoRA at scale. The prefix can't change the function class the model expresses — only the conditioning — and TS fine-tuning frequently needs new functional capacity. We ran the bake-off: prefix-30 was 5.8% MAPE vs LoRA rank-8's 5.1%.

7 · P-Tuning v2 (Liu et al. 2021)

Prefix Tuning, but applied at every layer instead of only the input. With deep prompts, P-Tuning v2 closed most of the gap to full fine-tuning on classification tasks. For TS forecasting we measured: 5.4% MAPE, between Prefix Tuning and LoRA. Fine but not better than LoRA, and Prefix-style methods can't merge cleanly — inference overhead.

8 · LongLoRA (Chen et al. 2023)

LoRA + a sparse-attention scheme for fine-tuning long-context models cheaply. Specifically: shifted-window attention during fine-tuning so the receptive field grows over the context, while the LoRA delta only sees a sparse pattern. Useful when you want to extend a base model's context length (e.g. TimesFM 2.5 trained on 16 K context, you want 64 K).

Not relevant for us yet — our 16 K context is plenty for daily fares. Could matter if we move to hourly intra-day forecasting (then we'd want 32 K–65 K context per series).

9 · VeRA — Vector-based Random Matrix Adaptation (Kopiczko et al. 2024)

Take LoRA but make B and A frozen random matrices shared across layers; train only two scaling vectors (b, d) per layer. Reduces trainable parameters by another order of magnitude over LoRA. Surprisingly competitive on instruction-following. Niche for TS — we haven't benchmarked but it's on the “cute idea” list.

Why we ship LoRA and not the cheaper IA3

The temptation is real: IA3 is 10× cheaper than LoRA. We benchmarked it on the 141-route panel and the result was 4.2 pp worse MAPE. The reason is the same as the reason Prefix Tuning underperforms: IA3 only rescales existing activations — family-specific structure isn't expressible as a rescaling of the pretrained weights. Specifically: TimesFM's pretraining has zero AA-route data, so the family-specific signal (e.g. transcontinental seasonality, Caribbean leisure surge) needs new directions in attention space, not just amplification of existing ones. LoRA gives those directions; IA3 doesn't.

The general rule. If your fine-tuning task is amplifying what the base model already knows, IA3 wins. If it is teaching the model to attend to new patterns, LoRA (or higher-rank methods) wins. Most TS panels are the second category.

Multi-LoRA serving (what we actually run)

Twenty route families → twenty LoRA adapters. We can't afford to keep twenty merged copies of the 200 M base in memory (4 GB each = 80 GB). Two production patterns: 

# Pattern A: hot-swap merged variants from pinned host RAM.
# Cost: 200 ms swap (PCIe transfer) per family.
# Used for nightly batch where we forecast all families sequentially.
families_pinned = {fam: load_merged_weights(fam, device='cpu', pin=True)
                   for fam in FAMILIES}
gpu_weights = clone_to_gpu(families_pinned[FAMILIES[0]])
for fam in FAMILIES:
    gpu_weights.copy_from(families_pinned[fam])  # 200ms PCIe
    forecasts[fam] = model(gpu_weights, batch[fam])

# Pattern B: keep base on GPU, apply LoRA delta dynamically.
# Cost: 8% inference latency (extra matmul per attention).
# Used for off-cycle re-score where we need to switch families per request.
base_gpu = load_base(device='cuda')
loras_gpu = {fam: load_lora(fam, device='cuda') for fam in FAMILIES}  # ~80MB total
def forecast(fam, x):
    return model(base_gpu, loras_gpu[fam], x)

We run Pattern A in production (nightly batch dominates the workload). Pattern B is used by the off-cycle re-score path where any of the 20 families may be requested in any order.

The fine-tuning recipe we ship

# Stage A: XReg head (linear probe with quantile head).
#   - Freeze TimesFM trunk.
#   - Train XReg head on (last_hidden_state, covariate_vector) -> quantile correction.
#   - 30 minutes on 1 A10G; 0.5 pp MAPE win on covariate-rich routes.
# Stage B: LoRA rank-8 on attention Q, K, V, O of all 20 layers.
#   - Freeze trunk + XReg head.
#   - Train LoRA per route family on 90-day fine-tune window.
#   - alpha = 16 (= 2 * r), AdamW, cosine schedule, lr = 5e-4.
#   - 6 hours on 1 A10G per family; ~3 pp MAPE win.
# Stage C: Optional joint fine-tune on a held-out validation set.
#   - Unfreeze XReg head + LoRA, freeze trunk.
#   - 1 hour additional; 0.1 pp MAPE win; not always run.

See finetuning.html for the full rank/alpha sweep and the production hot-swap pipeline.

Tradeoffs at AA's scale

DecisionCostBenefitWhat we accepted
LoRA rank 8 (not 16 or 32) ~0.1 pp MAPE behind rank-32 4× cheaper retrain; fits in 6 GB Diminishing returns past 16; rank-32 saved nothing in production
Attention-only LoRA (not + MLP) ~0.3 pp MAPE behind attention+MLP 30% of trainable params, 80% of the win Good enough; reconsider if MAPE budget tightens
LoRA over DoRA ~0.2 pp MAPE behind DoRA One less hyperparameter to sweep; mature tooling DoRA on watch-list; will swap when the next refresh ships
fp16/bf16 LoRA params (not int8) 2× storage Avoid quantization-aware training; merge math is exact Fine for 200 M base; would reconsider for 7 B+
One LoRA per route family (not per route) ~0.4 pp MAPE behind per-route on the most fine-tunable family 20 adapters not 6,700; manageable audit + retrain budget Family is the right shrinkage unit (matches business hierarchy)

Failure modes we encountered

  1. Catastrophic forgetting on cold-start. First experiment was “LoRA on every route.” Cold-start MAPE jumped from 10.2% → 13.4%. Fix: train per family, not per route; cold-start routes inherit family LoRA.
  2. LoRA + dropout interaction. The base model uses dropout 0.1; with LoRA the dropout scales the delta unevenly. Fix: turn off LoRA-specific dropout (already off in HuggingFace PEFT).
  3. Mismatched alpha/r. Setting alpha ≠ 2r changes the effective learning rate. Fix: pin alpha = 2r unless you sweep both jointly.
  4. Forgotten merge after rollback. After a rollback we shipped the base model with merged weights from the previous version. Fix: always carry the LoRA delta separately and merge at deploy time, not at training time.

Interview Q&A — PEFT methods

Walk me through LoRA in one minute.
For each weight matrix W you want to fine-tune, freeze it and add a learnable delta ΔW = BA where B is (d_in, r) and A is (r, d_out). Rank r is small (8 or 16), so trainable parameters scale linearly in r×d instead of quadratically. At inference, merge: W′ = W + (alpha/r)BA. Zero inference overhead. Hot-swappable adapters. The default PEFT method.
Why pick LoRA over IA3 if IA3 has 10× fewer params?
Because IA3 only rescales existing activations — it can't add new directions to attention space. For tasks where the fine-tune signal is genuinely new patterns (TS panels not in pretraining), LoRA dominates. We benchmarked: IA3 was 4.2 pp worse MAPE than LoRA rank-8 on our 141 routes.
When would you reach for DoRA?
When LoRA has a residual gap to full FT and you can spend ~12% more training time. DoRA decomposes the pretrained weight into magnitude + direction, fine-tunes both. We measured 0.2 pp MAPE improvement over LoRA on our most fine-tunable family. On the watch list for the next refresh; not deployed yet.
When does QLoRA matter and when is it overkill?
QLoRA matters when the base model is >= 7 B parameters and you can't fit fp16 weights on your GPU. NF4 base + LoRA delta + paged optimizer is the only way to fine-tune a 70 B model on a 48 GB GPU. For our 200 M base it's overkill — fp16 weights fit on a phone GPU, and quantization noise in the base is a real cost (we measured 0.4 pp MAPE inflation on TS).
What's the math behind alpha = 2r?
The LoRA delta is scaled by alpha/r. If you keep alpha/r constant (e.g. 1 or 2), the magnitude of the delta is independent of rank, so when you sweep rank you're only varying expressiveness, not effective learning rate. alpha = 2r is a common stable default; alpha = r matches the original paper. The pathological case is alpha = const, rank = sweep, which conflates two effects.
How do you serve 20 LoRA adapters efficiently?
Two patterns. (1) Hot-swap: pre-merge all 20 variants, store in pinned host RAM, copy to GPU on family switch (~200 ms PCIe). (2) Dynamic delta: keep base on GPU, apply LoRA delta at inference (~8% latency cost). We use pattern 1 for nightly batch (one family at a time) and pattern 2 for off-cycle re-score (any family, any time). The 80 MB total LoRA size makes it cheap to hold all on GPU.
Why prefer LoRA over Adapter when both can swap?
LoRA merges into existing weights; Adapter inserts new layers. After merge, LoRA has zero inference overhead; Adapter is permanently 10% slower. For high-throughput batch inference (our nightly run is 13,400 forecasts), 10% latency adds up. Adapter is still useful when you want pre-merged adapter swapping at no swap cost — but pinned-RAM LoRA gets us there too.
Why didn't Prefix Tuning win?
Prefix Tuning can't change the function class — it only changes the conditioning. For tasks where fine-tuning needs to teach the model new feature interactions (most TS panels), prefix tokens have no way to express them. P-Tuning v2 (deep prompts at every layer) closes some of the gap but can't merge cleanly, so inference is permanently slower. LoRA wins because it can express new directions and merge for free.
What's the catastrophic-forgetting story for LoRA?
LoRA is far better than full FT but not immune. If you train on 141 routes, the trunk hidden states reflect those 141 routes' distribution. Cold-start routes outside that distribution see a worse forecast through a LoRA-warped trunk. Mitigation: train per family and have cold-start routes inherit the family LoRA — or skip LoRA entirely and run zero-shot for the first 90 days, which is what we do.
What about VeRA and the “1000 adapters per LLM” story?
VeRA freezes B and A as random shared matrices and trains only per-layer scaling vectors — trainable parameters drop another 10×. Useful when you have hundreds of tasks and want sub-MB adapter storage. For TS we have 20 family adapters and storage isn't a constraint, so the gain doesn't justify the LoRA-vs-VeRA accuracy gap. We watched it; we don't use it.
If you had to fine-tune a 70 B foundation TS model tomorrow, what stack?
QLoRA (NF4 base) + DoRA on attention + paged optimizer. NF4 because fp16 70B doesn't fit on any reasonable GPU. DoRA because at that scale every accuracy point matters. Paged optimizer because forward-backward memory spikes need overflow to CPU. Then merge for inference and hot-swap by family. Same recipe as ours, scaled.
