Azure deployment architecture

American Airlines runs on Microsoft Azure. This page is the Azure-specific deployment topology for the AA pricing forecast service: which Azure services handle which responsibilities, why each was chosen over alternatives, and the AA-specific compliance considerations (data residency, FedRAMP, FAA audit trails).

TL;DR. The service runs entirely on Azure: Azure Machine Learning for the model registry and training jobs, NV A10 v5 spot VMs for nightly inference, Azure Blob Storage (hot tier for the feature store), Azure Cosmos DB for low-latency model-pointer reads, Azure Cache for Redis for forecast caching, Azure Synapse for the analytical warehouse, Azure Data Factory (with a self-hosted Airflow alternative on AKS) for orchestration, Azure Container Registry for images, and Application Insights + Azure Monitor for telemetry. Microsoft Entra ID handles auth. Total monthly cloud spend: ~$340 (compute) + ~$60 (storage / monitoring).

Why Azure

Not a model decision — an org decision made years before this project. AA chose Azure as its primary cloud for several reasons that shape how we build:

  • Microsoft Enterprise Agreement: AA has a multi-year EA that gives volume discounts and committed-spend pricing. Building on Azure capitalizes on those discounts; building on AWS would be billed at retail.
  • Microsoft Entra ID integration: The corporate identity provider is Entra ID (formerly Azure AD). Native Azure services federate without extra IdP setup.
  • Compliance posture: Azure Government Cloud and FedRAMP High coverage matter for the regulated parts of AA's footprint (DOT-touching systems). The ML service does not need FedRAMP High but lives next to systems that do.
  • Existing ML platform: Azure ML has been the org-standard ML platform since 2022. Reusing the registry, compute targets, and pipelines beats building parallel infrastructure on another cloud.
  • Data gravity: The AAdvantage warehouse, Sabre PSS extracts, and the operational telemetry all land in Azure-native stores. Egress to AWS would be both expensive and slow.

Why we use Azure spot VMs

Azure Spot (chosen)

  • ~70-80% discount on compute vs pay-as-you-go.
  • Eviction is rare in the 02:00-02:30 CST window (low demand).
  • The job is fault-tolerant: if evicted, we re-trigger and re-run (idempotent writes to Cosmos).
  • Annual compute bill ~$5 vs ~$25 on-demand.

Why we don't use reserved instances

  • The job runs ~2 minutes/day. Reserving 24/7 capacity is wasteful.
  • Off-cycle re-scoring is bursty — doesn't map well to fixed reservation.
  • Spot eviction risk is acceptable because we have a 30-minute SLA buffer (02:30 CST deadline vs ~02:02 actual).

The Azure ML pipeline for training

Stage A and Stage B retrains run as Azure ML pipelines, not as ad-hoc scripts. Each pipeline is versioned in Azure DevOps, runs in a managed compute cluster, and publishes signed artifacts to the Azure ML registry. 

# azureml/pipelines/stage_a_xreg_head.yaml
$schema: https://azuremlschemas.azureedge.net/latest/pipelineJob.schema.json
type: pipeline
display_name: aa_pricing_stage_a_xreg_head
experiment_name: aa-pricing
compute: azureml:gpu-cluster-a10  # NV36ads A10 v5

settings:
  default_datastore: azureml:aapricing_blob_hot
  continue_on_step_failure: false

inputs:
  train_data:
    type: uri_folder
    path: azureml:aa_pricing_train_v1@latest
  base_model:
    type: custom_model
    path: azureml:timesfm-2.5-200m@latest
  config:
    type: uri_file
    path: azureml:stage_a_config@latest

outputs:
  trained_head:
    type: custom_model
    name: aa-timesfm-xreg-head
  metrics:
    type: uri_file

jobs:
  train_step:
    type: command
    component: azureml:train_xreg_head_component@latest
    inputs:
      train_data: \${{parent.inputs.train_data}}
      base_model: \${{parent.inputs.base_model}}
      config: \${{parent.inputs.config}}
    outputs:
      trained_head: \${{parent.outputs.trained_head}}

  eval_gate:
    type: command
    component: azureml:eval_gate_component@latest
    inputs:
      candidate: \${{parent.jobs.train_step.outputs.trained_head}}
      gate_thresholds:
        mape_max: 6.0
        coverage_min: 78
        coverage_max: 82
        ece_max: 0.04
    outputs:
      decision: \${{parent.outputs.metrics}}

AA-specific compliance considerations

  • Data residency. All AA US-domestic OD-pair data lives in eastus2 region; transatlantic data lives in westeurope. The model artifacts are registered separately per region; no cross-region replication of fare data without explicit legal sign-off.
  • FAA audit trail. Every forecast write is append-only to a Blob container with the immutable storage tier (legal hold) and 7-year retention. Forecast decomposition (baseline + sum(covariate_contributions)) is stored alongside the forecast. Auditors can reconstruct any historical fare decision.
  • PII boundary. The forecast service never touches PNRs or named-passenger data. Inputs are aggregated daily fare and load-factor metrics. PII separation is enforced at the Synapse warehouse level via row-level security.
  • Antitrust / fare-rule compliance. The model produces a forecast distribution; the C++ optimizer applies pricing policy. Both are versioned and independently auditable. The pricing policy is reviewed by AA Legal quarterly; the model is reviewed against bias / disparate-impact heuristics by Compliance.
  • Vendor risk for foundation models. Google's TimesFM weights are pinned at v2.5 in the AA-internal Azure ML registry. We do not auto-pull the latest from HuggingFace at inference. Re-pulling new versions requires a Compliance review.

What I would build differently if I had to start over

  1. Use Azure ML batch endpoints from day one for the inference path. We initially rolled our own AKS-scheduled spot VMs because Azure ML batch endpoints had a 10-minute cold-start at the time of project start; the new Managed Compute features cut that to ~30 s. Batch endpoints would be one less Kubernetes manifest to maintain.
  2. Microsoft Fabric Real-Time Analytics for the calibration drift dashboard. Currently we use Application Insights custom metrics + Azure Monitor workbook, which works but is rigid. Fabric's KQL-based explore would be faster.
  3. Azure Confidential Computing for the audit-log component. The 7-year forecast retention is sensitive; a confidential VM would give us tamper-evident logs with hardware attestation. Not currently in scope but on the roadmap.

Interview Q&A

Why did you build this on Azure rather than AWS or GCP?
Org-level decision, not a model decision. AA has a Microsoft Enterprise Agreement that gives committed-spend discounts; corporate identity is on Microsoft Entra ID; the AAdvantage warehouse, Sabre extracts, and operational telemetry already live in Azure (data gravity). Building on AWS would have been retail-priced compute and cross-cloud egress. Building on Azure capitalizes on the existing footprint.
Walk me through how the nightly batch survives Azure spot eviction.
Three layers. (1) The batch is idempotent: Cosmos DB writes are upserts keyed by (route, departure_date, run_id), so a re-run overwrites the same partition with no duplication. (2) Azure Data Factory's job-retry policy kicks in within 60 seconds of an eviction, with exponential backoff. (3) The full job is 2 minutes; even with one eviction we hit the 02:30 CST SLA. We've seen ~3 evictions in 26 weeks; all recovered automatically.
Why Cosmos DB instead of Azure SQL for forecast storage?
Read pattern. The optimizer reads forecasts ~200M times a day, partitioned by departure_date and route. Cosmos DB's partitioned point-read latency is <5 ms p99 at this query pattern; Azure SQL would need careful index design and would not match it. Storage volume is small (~30 MB/day), so Cosmos's storage cost isn't a factor. The cost is in RU/s — we provisioned 4,000 RU/s based on the read pattern.
How do you handle Microsoft Entra ID for service-to-service auth?
Managed identities. The inference VM has a system-assigned managed identity that has Storage Blob Data Reader on the feature-store container, Cosmos DB Data Contributor on the forecast container, and Key Vault Secrets User on the cosign-key vault. No passwords or keys in code. The identity is provisioned by an ARM template (managed via Azure DevOps) so revocation is auditable.
What does Microsoft Purview give you that Azure ML doesn't?
Cross-system lineage. Azure ML tracks the model artifacts and training jobs but not the upstream data sources (Sabre, AAdvantage warehouse, ATPCO). Purview catalogs all of those, builds the column-level lineage from source → Synapse → Blob → Azure ML training input, and lets compliance reviewers trace any production fare back to its raw inputs. This is the FAA audit story end-to-end.
Why use Application Insights instead of Datadog?
Two reasons. (1) Native integration: App Insights instruments Azure-deployed code with one SDK call and integrates with Entra ID auth automatically. Datadog requires per-service API keys and a sidecar agent. (2) Cost: at our log volume (~200 GB/month), App Insights is ~30% cheaper. We do export aggregated metrics to Datadog for cross-cloud teams that prefer one pane of glass, but App Insights is the source of truth.
Could this run on Azure Government Cloud if needed?
Yes — the architecture maps 1:1 to Azure Government services. The TimesFM weights are open-source; they would need to be re-vetted under the Government Cloud's third-party software policy. The Azure ML, Cosmos DB, Blob Storage, Synapse, and AKS services all have Government variants. The application code would not change; only the deployment target ARM templates would. Not currently in scope but architecturally feasible.
