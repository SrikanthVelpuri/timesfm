Inference optimization — the 47× speedup, layer by layer

The nightly batch of 6,700 OD-pairs has to complete in <90 s on a single A10G spot instance. Naive PyTorch (FP32, batch=1, eager mode) takes 31 minutes. The shipped path runs in 41 seconds at $0.011 per nightly batch. Each optimization is independently rollback-able; this page is the layered stack, with the code at each layer.

TL;DR. Stack: batching (15.6×) → BF16 (2×) → torch.compile (1.5×) → pinned-memory LoRA hot-swap. Median latency 280 ms → 6 ms per OD-pair. p99 14 ms. Throughput 3.6 → 165 series/sec. Cost per nightly run $0.205 → $0.011. Annual inference cost <$50.

Order matters. Batching alone got 80% of the win. The order is "cheap, high-leverage first". Doing torch.compile before batching is a waste — you compile a graph that runs at 280 ms instead of 18 ms.

Layer 1: batching (the biggest win)

TimesFM's API takes a list of input series and parallelizes across the batch axis. "Batching" is just “make the list longer”. 

# Before: one OD-pair at a time
for od_pair in od_pairs:                        # 6,700 iterations
    point, q = model.forecast_with_covariates(  # 280 ms each
        inputs=[fare[od_pair]],
        ...,
    )

# After: 64 at a time, grouped by route family
for chunk in chunked_by_family(od_pairs, size=64):  # 105 iterations
    inputs = [fare[od] for od in chunk]
    point, q = model.forecast_with_covariates(      # 18 ms / OD amortized
        inputs=inputs,
        dynamic_numerical_covariates={...},
        static_categorical_covariates={...},
    )

Why grouping by family

Each route family has its own LoRA adapter. If you shuffle the batch, you swap adapters mid-batch — the swap cost dominates. Sort by family, you swap once per chunk. First version of this code shuffled and was 3× slower than necessary.

Layer 2: BF16 mixed precision

A10G's tensor cores execute BF16 matmuls at 2× the throughput of FP32 with no accuracy loss for inference at this scale. 

import torch

with torch.autocast(device_type="cuda", dtype=torch.bfloat16):
    point, q = model.forecast_with_covariates(...)

Why BF16 and not FP16

FP16 has a much smaller dynamic range (max ~6.5e4 before overflow). With fares spanning $80–$11,000 the loss of precision at the high end was visible in q90 (~0.4% drift). BF16 has FP32's exponent range, just less mantissa, so dynamic range is preserved. No measurable accuracy delta vs FP32.

FP32: 1 sign, 8 exp, 23 mantissa  ·  BF16: 1 sign, 8 exp, 7 mantissa  ·  FP16: 1 sign, 5 exp, 10 mantissa

Caught one bug

The XReg head was still in FP32 (trained without autocast). The cast at the FP32 → BF16 boundary was eating 6% of inference time. PyTorch Profiler caught it — kernel mix showed a stray FP32 GEMM right at the head. Re-trained with autocast on, problem disappeared.

Layer 3: torch.compile

model = timesfm.TimesFM_2p5_200M_torch.from_pretrained(...)
model.compile(timesfm.ForecastConfig(...))           # TimesFM-side compile

# AND wrap the call site
forecast_fn = torch.compile(
    model.forecast_with_covariates,
    mode="reduce-overhead",     # CUDA graphs under the hood
    fullgraph=False,            # tolerate dynamic shapes
)

What each flag does

  • mode="reduce-overhead": uses CUDA graphs to eliminate kernel-launch overhead. Big win for short-running kernels typical of batch-64 transformer inference.
  • fullgraph=False: TimesFM has data-dependent control flow (variable-length context handling). Forcing fullgraph fails compile; False produces multiple compiled subgraphs, each fast.

Compile cost

~12 seconds the first time the function is called. Amortized over 105 batches per nightly run, this is 0.1 s per batch — trivial. Watch out for recompilation: if input shapes vary unpredictably, torch.compile recompiles, which can cost minutes. Solution: pad to fixed shapes per family. 

# Pad final partial batch to 64 with dummy series; discard their outputs.
# Cost: ~1% wasted compute on tail batch.
# Benefit: zero recompilation in steady state.

if len(chunk) < 64:
    pad = 64 - len(chunk)
    chunk = chunk + [DUMMY_SERIES] * pad
    point, q = forecast_fn(inputs=chunk, ...)
    point = point[:-pad]   # discard dummies
    q = q[:-pad]

Layer 4: LoRA hot-swap with pinned memory

The naive LoRA swap costs ~800 ms (re-load adapter from disk, transfer to GPU). My target was <10 ms.

The path that worked

  1. Preload all 17 adapters at service startup into pinned CPU memory (tensor.pin_memory()). Total RAM: ~80 MB. Cost: ~600 ms once, at startup.
  2. Apply via in-place state-dict update on the resident GPU model. PyTorch handles the H2D transfer with the pinned source — significantly faster than pageable memory. Each swap: ~6–10 ms.
  3. Group batches by family so the swap rate is one per ~3.8 batches, not one per OD-pair.
import safetensors.torch as st

class LoraRegistry:
    def __init__(self, families, base_path):
        self.adapters = {}
        for family in families:
            sd = st.load_file(f"{base_path}/{family}.safetensors")
            self.adapters[family] = {
                k: v.pin_memory() for k, v in sd.items()
            }

    def apply_(self, model, family):
        # In-place LoRA-only update. Base weights untouched.
        with torch.no_grad():
            for k, v in self.adapters[family].items():
                # k is like 'attn.q_proj.lora_A.weight'
                target = model.get_parameter(k)
                target.copy_(v, non_blocking=True)
        torch.cuda.synchronize()

# Per batch
if family != current_family:
    registry.apply_(model, family)   # ~8 ms
    current_family = family
out = forecast_fn(inputs=chunk, ...)

Pinned memory math

  • Pageable CPU → GPU (default): ~62 ms per 4 MB adapter
  • Pinned CPU → GPU: ~8 ms per 4 MB adapter
  • Win: ~8×. Per-day savings: 105 batches × ~50 ms saved = 5 s. Not huge in absolute terms but it's the difference between hitting the SLO and missing it on bad days.

Layer 5: forecast caching

Some OD-pairs get re-scored mid-day (competitor undercut, fuel update). If the covariates haven't changed materially, the forecast hasn't changed.

  • Cache key: (od_pair, departure_date, snapshot_date, sha256(quantized_covar_block))
  • Cache value: forecast tensor + quantile tensor
  • Backing store: Redis with 24-hour TTL
  • Hit rate in production: ~37% on intra-day re-runs

Why quantize covariates before hashing

Without quantization, every floating-point reload looks "new" to the cache (e.g., fuel went from $2.847291 to $2.847294 due to source rounding). Quantize fuel to $0.01, competitor fare to $1, DTD to integer days, load factor to 0.005. Then hash. This was the biggest cache-rate improvement — 4% → 37%.

What I tried that did NOT work

An honest dead-end log. These are common interview traps; here is why each was rejected.

Approaches that did work

  • Batching (15.6×)
  • BF16 (2×)
  • torch.compile (1.5×)
  • LoRA hot-swap (cost reduction)
  • Forecast caching (off-cycle savings)

Approaches I rejected

  • INT8 dynamic quantization — coverage dropped to 73%
  • ONNX + TensorRT — 5% kernel coverage gap
  • Speculative decoding — horizon math doesn't fit
  • Multi-GPU sharding — doubled cost for 1.6× speed
  • Tensor parallelism — same as above
  • Static-batch CUDA graphs without compile — covered by torch.compile

Why INT8 quantization failed (the most painful no)

torch.quantization.quantize_dynamic on the linear layers cut latency to 4 ms but degraded q10/q90 calibration noticeably (coverage 79% → 73%). Bid-price-grade quantiles are precision-sensitive. Two diagnostic findings:

  1. The XReg head's coefficients have small absolute values (~0.01–0.1) on covariates with large values (e.g., fuel coefficient $11.4 / $1 fuel). INT8 quantization rounds the small coefficients to 0, eliminating the covariate's contribution.
  2. The quantile head is the most precision-sensitive layer because it has to maintain monotonicity (q10 < q20 < ... < q90). Even small INT8 rounding flips the ordering on flat-fare days.

Could revisit with calibrated INT8 or per-channel quantization, but the savings (4 ms → 4 ms with calibration overhead) are not worth the engineering. Kept BF16.

Why ONNX + TensorRT failed

Exported to ONNX, ran through TensorRT 8.6. The exported graph had ~5% kernel coverage gap that fell back to CUDA, eliminating the expected speedup. With torch.compile already at 6 ms, TensorRT's incremental gain was <1 ms in the best case — not worth the operational complexity of maintaining two model formats. Operational complexity here means: ONNX export pipeline, version pinning of TRT, separate benchmark suite, separate rollback target. Not an engineering win.

Profiling discipline

Every checkpoint goes through PyTorch Profiler before merge: 

from torch.profiler import profile, ProfilerActivity, schedule

with profile(
    activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],
    schedule=schedule(wait=1, warmup=2, active=4, repeat=1),
    on_trace_ready=lambda p: p.export_chrome_trace("trace.json"),
    record_shapes=True,
    profile_memory=True,
) as prof:
    for batch in test_batches:
        forecast_fn(inputs=batch, ...)
        prof.step()

Open trace.json in Chrome's chrome://tracing. Look for:

  • Stray FP32 kernels in a BF16 graph (the bug I caught early on).
  • Long gaps between kernels (kernel-launch overhead → torch.compile with reduce-overhead).
  • D2H copies during the hot path (synchronous CPU access → should be async).
  • Recompilation events (input shape changed → pad to fixed).

Interview Q&A

Walk me through your approach to optimizing this inference path.
Start with profiling, not assumptions. Run baseline, look at the kernel mix and time-per-batch. Identify the hot path. Apply the cheapest, highest-leverage change first — in this case batching, which gave 80% of the final speedup. Then iterate: BF16, torch.compile, hot-swap. Each change is independently rollback-able. Re-profile after each change to confirm the kernel mix matches expectations.
Why didn't you use TensorRT?
5% kernel-coverage gap fell back to CUDA, killing the expected speedup. With torch.compile already at 6 ms, TensorRT's incremental gain was <1 ms while doubling the operational surface. Optimization is about cost per ms saved; TRT was a bad ratio. Would revisit if torch.compile capped out and we needed more.
How do you choose batch size?
Empirical sweep on production hardware. Watch latency-per-item, peak VRAM, and tensor-core utilization. Pick the batch where (a) latency-per-item plateaus, (b) VRAM has ≥50% headroom for safety, (c) you don't hit recompilation in steady state. For us that was 64 on A10G; would be ~256 on A100.
Why does batching help so much for transformer inference?
GPU tensor cores execute matmuls in fixed-size tiles (e.g., 16×16 BF16). At batch=1 you process a "batch" of one row, leaving most of the tile unused. At batch=64 the tile is fully utilized, so you get 64× the work for the same kernel-launch and memory-traffic overhead. The same matmul kernel runs — you're paying its fixed cost more efficiently.
What does CUDA graphs (the “reduce-overhead” mode) actually do?
Captures the sequence of CUDA kernel launches into a graph object, then replays the whole graph in one CPU→GPU command instead of N separate launches. For short-running kernels (typical of batch-64 transformer inference where each kernel is ~50–200 µs), the launch overhead (~5 µs per launch) is a meaningful fraction. Eliminating it gives a 1.3–1.6× speedup, depending on kernel mix.
How would you scale this to 100,000 OD-pairs instead of 6,700?
Stays single-A10G if we accept ~10 minute wall time. To stay at 41 s wall time we'd need ~16× throughput. Options ranked by cost/benefit: (1) larger batch on A100 (40 GB VRAM) — batch=512, ~3× throughput; (2) data-parallel across 4×A10G — near-linear scaling; (3) move from BF16 to mixed FP8 with H100 — ~2× on FP8 matmuls. Avoid model parallelism — the model is small enough that DP wins.
How do you ensure your optimizations don't change accuracy?
CI gate. Every checkpoint runs the eval harness on a frozen mini-cohort and reports MAPE plus 80% PI coverage. Any change that drifts MAPE by >0.05 pp or coverage by >1 pp blocks merge. We caught the BF16 calibration bug, the LoRA dropout bug, and the INT8 calibration drop with this gate. The gate is the single most important piece of MLOps in the project.
If you had to cut one optimization, which would you cut?
Forecast caching. The hit rate (37%) is real but the operational complexity (Redis, cache key design, quantization-aware hashing, TTL management) costs more engineering than the latency savings justify in steady state. The other four optimizations — batching, BF16, compile, hot-swap — are essentially free in operational complexity and would all stay.
