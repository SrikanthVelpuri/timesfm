Fine-tuning strategy — PEFT method selection

AA has no continued-pretraining budget. The Google base weights stay frozen. The decision was: which subset of the model do we update, and how do we update it? This page is the parameter-efficient-fine-tuning (PEFT) comparison and the math behind the chosen approach.

TL;DR. Two-stage strategy: (1) fine-tune the XReg regression head end-to-end with frozen trunk to learn AA covariate elasticities, then (2) add rank-8 LoRA adapters on attention Q/K/V/O projections per route family for the top-200 OD-pairs. Total trainable parameters: ~3.2 M (1.6% of base model). Total quarterly compute: ~$7. MAPE: 10.2% → 6.0% → 5.1%. Full fine-tune was rejected at $45K/quarter for a 0.4 pp gain.

Why PEFT and not full fine-tuning

A 200 M-param model fully fine-tuned on AA's ~2.8 M training windows would cost around $45,000 of GPU spot per quarter and produce a ~800 MB artifact per route family if we wanted family-specific models. PEFT gives 85% of the accuracy gain at 0.02% of the cost and produces ~4 MB artifacts.

The math, briefly:

full FT: train all W ∈ Θ — ~200 M params updated, gradients held for all
LoRA: W' = W + (α / r) · B A, where A ∈ ℝr×k, B ∈ ℝd×r, r << min(d, k)

For TimesFM with hidden dim 1280 and a target attention matrix that is 1280×1280, a LoRA rank-8 adapter has 1280×8 + 8×1280 = 20,480 params instead of 1.638 M. Multiply by 4 attention projections (Q/K/V/O) and 20 transformer blocks: 1.6 M LoRA params per route family vs 130 M for full fine-tuning of the same matrices. ~80× less compute.

Stage A: XReg head (Linear probe with quantile head)

  • Inputs: TimesFM's baseline forecast residuals + the AA covariate stack.
  • Architecture: L2-regularized linear core + rank-32 cross-route interaction term + 10-quantile output.
  • Loss: pinball loss on all 10 quantiles + median MSE, equally weighted (0.5 / 0.5).
  • Training: ~250 K windows, 3 epochs, ~40 min on 1×A10G, $0.70.
  • Why this is “PEFT”: trunk is frozen; only the head and the rank-32 cross term train. ~300 K params.

Stage B: LoRA rank-8 on attention

  • Targets: Q, K, V, O projections in all 20 transformer blocks.
  • Rank: 8 (chosen via sweep over {4, 8, 16, 32}).
  • Alpha (LoRA scaling): 16 (so α/r = 2.0).
  • Init: A ~ N(0, 0.02), B = 0 (Kaiming-style for the input projection, zero for output to start as identity).
  • Training: ~50 K windows per family, 1 epoch, ~6 min per family, ~$0.30 each.
  • Output: 17 of 20 families ship; 3 fail the ≥0.5 pp gate and fall back to head-only.

The LoRA rank sweep

Why rank 8? Empirical sweep on a representative family (Transcontinental hub):

RankParams / familyTrain time / familyVal MAPEVerdict
r = 4~800 K~4 min5.4%Underfits family-specific patterns
r = 8~1.6 M~6 min5.1%Chosen — best ROI
r = 16~3.2 M~10 min5.0%0.1 pp gain not worth 2× storage / train time
r = 32~6.4 M~18 min5.0%Saturates
Pattern: for low-data fine-tunes (50K windows), LoRA capacity saturates fast. The choice between r-8 and r-16 is essentially “trade 0.1 pp MAPE for half the storage, half the train time, and half the swap latency.” All operational, so r-8 wins.

How we hot-swap LoRA at inference

The naive load-from-disk swap is ~800 ms (read safetensors, transfer to GPU, apply). That kills the nightly batch budget. The path we shipped: 

# At service startup (once, ~600 ms total)
adapters = {}
for family in FAMILIES:                       # 17 families
    sd = safetensors.load_file(f"adapters/{family}.safetensors")
    adapters[family] = {                      # pin to CPU memory
        k: v.pin_memory() for k, v in sd.items()
    }

# Per batch (amortized ~8 ms per family change)
def run_batch(family, inputs, covar):
    if family != current_family:
        model.lora_state_dict_update_(adapters[family])  # in-place
        current_family = family
    return model.forecast_with_covariates(...)

The lora_state_dict_update_ helper is ~30 lines of PyTorch that copies only the LoRA tensors (A and B per layer) from pinned CPU memory into the resident GPU model. Base weights never move.

Why pinned memory matters

PyTorch's default state_dict.update() with pageable CPU source tensors triggers an extra copy through the OS's page cache. With pinned memory, the H2D DMA goes straight from CPU to GPU. ~8× faster for the LoRA-sized payload (~4 MB):

  • Pageable CPU → GPU: ~62 ms
  • Pinned CPU → GPU: ~8 ms

What I almost shipped wrong

  1. Trained LoRA on Q only, not on all of QKVO. Saves params but missed cross-attention patterns. Rank-16 on Q alone (3.2 M params) underperformed rank-8 on QKVO (1.6 M params) by 0.4 pp. Targeting the right matrices matters more than rank.
  2. Used alpha = rank first. The original LoRA paper's "scale by α/r" lets you change rank without re-tuning effective learning rate — we want α/r to be a fixed effective LR scaling. We set α=16, so r-8 has α/r = 2.0 and r-16 has α/r = 1.0. Without this convention, rank changes also changed effective LR and the sweep was noisy.
  3. Forgot to disable the dropout in the LoRA layers at inference. Standard PyTorch eval mode handles this; I had a custom inference path that bypassed it. Calibration drifted ~0.7 pp until I noticed.

Composability with the XReg head

Stage A and Stage B are independent. The shipped service runs:

forecast = TimesFMbase + LoRA(family)(history) + XReghead(covariates)

Either component can be rolled back independently. If a LoRA family fails CI gate, we drop the adapter and fall back to TimesFM-base + XReg head — the service degrades gracefully to Stage-A quality on that family. The XReg head, by contrast, is universal and always loaded.

Interview Q&A

Why LoRA over adapter modules (Houlsby/Pfeiffer)?
Two reasons. (1) Inference latency: adapters insert bottleneck layers in the forward pass — you pay them every batch. LoRA is mathematically added to existing weights and can be merged at inference (W′ = W + α/r · BA), so the latency is identical to base model. (2) Composability: with LoRA we can hot-swap per family in 8 ms; with adapters we'd need to physically replace network layers between batches.
Why didn't you use QLoRA?
QLoRA is 4-bit base + LoRA. The win is memory: the base model takes ~300 MB instead of ~800 MB. We had no memory pressure (~3 GB peak on a 24 GB A10G), so QLoRA only added a 10% inference-latency penalty from runtime de-quantization with no offsetting benefit. QLoRA shines when fine-tuning at small VRAM (consumer GPUs, hosted GPUs with 16 GB). Not our case.
How did you set the LoRA dropout?
0.05 on the rank dimension. Larger dropout (0.1+) hurt convergence; lower (0.0) overfit on the smaller families. The dropout has to be disabled at inference (module.eval()) — I once shipped a build that left it on and saw 0.7 pp coverage drift before debugging.
What happens if you train LoRA at rank 1?
Tried it. MAPE 6.4% — worse than the head-only baseline (6.0%) for the family I tested on. With rank 1 the LoRA captures only one direction of variation; it actively interferes with the base model's ability to use other directions. Below rank ~4 the LoRA hurts more than it helps. Empirical, not theoretical — the original paper's claim that rank 1 works on language-model fine-tunes does not transfer to TimesFM.
How do you decide which layers to LoRA-target?
Two signals. (1) Layer-wise gradient magnitudes during a brief full fine-tune probe — layers with the largest gradient L2 are the ones that "want to change". (2) Ablation: hold out one layer family at a time and measure MAPE delta. For TimesFM, attention QKVO dominates; FFN and embeddings did not improve enough to justify the extra params. We do not LoRA the output head or quantile head — those are tuned by Stage A.
What's the relationship between LoRA rank and effective learning rate?
The original paper's formula W′ = W + (α/r) · BA means the contribution magnitude is independent of r if you scale α with r. We fix α=16 so r-4 has stronger update magnitude than r-16; the rank only changes capacity, not LR. This is the convention used in HuggingFace's PEFT library and matters when you sweep rank — otherwise rank changes confound with effective LR changes and your sweep results are misleading.
If you could afford full fine-tuning, would you do it?
No. Two reasons beyond cost. (1) Catastrophic forgetting risk: full FT on AA data could degrade zero-shot performance on long-tail OD-pairs that don't see fine-tune examples. LoRA + frozen trunk preserves the foundation prior by construction. (2) Auditability: with frozen trunk + small LoRA delta, I can produce a layer-wise diff vs the Google base for compliance review. Full FT would give a 200 M-param diff that nobody can audit.
